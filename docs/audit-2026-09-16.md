# Audit du projet — 16 septembre 2026

Audit externe demandé à 24 jours de l'échéance. Méthode : lecture intégrale
de la documentation, exécution de la suite de vérification locale, trois
revues de code indépendantes (backend, ML/données, frontend) avec
reproduction des défauts signalés, et vérification sur Internet des règles
officielles, des versions et des travaux concurrents. Les corrections de code
ne sont **pas** appliquées par cet audit ; elles sont priorisées dans
[plan-soumission.md](plan-soumission.md).

## Verdict

Le projet a une gouvernance scientifique rare pour un hackathon : manifestes
et checksums, split groupé verrouillé, protocole d'accès test unique, REX
datés, aucun chiffre non versionné. Ses faiblesses sont ailleurs :

1. deux blocages administratifs (dépôt privé, pas de licence) ;
2. aucun modèle appris n'apporte encore de preuve : le classifieur de qualité
   n'est pas dans le produit et ne bat pas le raccourci d'acquisition ;
3. le split « anti-fuite » laisse passer des séries longitudinales
   (dates consécutives, mêmes lignées) ;
4. le produit casse sur des cas de démo réalistes (TIFF 16 bits, lot > 25 Mo,
   import et analyse couplés) ;
5. la grille d'évaluation documentée n'était pas celle de l'organisateur.

Les points 3 à 5 sont corrigeables en une semaine ; le point 2 est le seul
travail scientifique restant et il doit être borné.

## Constats scientifiques (ML et données)

### Élevé

| # | Constat | Preuve | Recommandation |
|---|---|---|---|
| S1 | **Fuite longitudinale** : le groupe `YYMMDD` sépare des jours, pas des lots de puces. 21 paires de dates distantes de ≤ 3 jours partagent une lignée de part et d'autre d'un split ; 345 des 473 images test appartiennent à une date voisine d'une date train/validation (`230523` train jour 0–1 → `230524` test jour 2–3 → `230525` train, HPMEC). | recalcul depuis `data/splits/ooc-grouped-v1.csv` ; `split_ooc.py:114-193` ; limitations `split_ooc.py:700-719` ne le mentionnent pas | split v2 par « campagnes » (dates ≤ 3 jours et lignée commune fusionnées) **avant** le run GPU ; phrase explicite dans le rapport |
| S2 | **Aucune preuve d'apprentissage au-delà du raccourci** : handcrafted test macro-F1 0,692 contre 0,695 pour mode + résolution seuls ; seule la ROC-AUC diffère (0,803 / 0,714). Le prétraitement CNN amplifie le raccourci : réplication L→RGB (les images RGB sont `good` à 83 % en test contre 39 % pour `L`), réduction 2056×1542 → 224×168 qui efface le signal haute fréquence définissant la qualité. | `reports/ooc-grouped-split-v1.json`, `reports/benchmarks/ooc-handcrafted-image-quality-v1.json`, `preprocessing.py:17-21`, `:41-51` | recadrage commun, niveaux de gris, ≥ 512 px ou tuiles ; balanced accuracy **par mode** comme métrique primaire ; GroupKFold sur les 50 groupes train+validation |
| S3 | **Le CNN n'a jamais tourné en `validation` et rien dans le produit ne classe la qualité** : `runtime.py:21-23` n'enregistre que le moteur adaptatif ; `onnxruntime` absent de `backend/pyproject.toml` ; le notebook contient des `REPLACE_WITH…`. | `backend/app/ml/runtime.py`, `notebooks/ooc-cnn-kaggle.ipynb` | run GPU puis moteur `ooc-image-quality-cnn` via ONNX Runtime, ou QC explicite de repli |

### Moyen

- S4 — le test « gelé » est lisible et déjà évalué hors protocole :
  `data/splits/ooc-grouped-v1.csv` versionne les labels test ;
  `train_ooc_baseline.py:333-344` charge features et labels test dans le
  processus de sélection ; `split_ooc.py:498-511` publie la distribution des
  labels test par mode. Le protocole à reçus ne protège que le CLI CNN.
- S5 — bruit intra-groupe non quantifié : 116 paires dHash ≤ 8 dans le jeu,
  dont 26 à labels contradictoires et 97 à lignées différentes ; plafond de
  performance et indice que les images d'une date viennent des mêmes puces.
- S6 — contrat runtime trop strict : `runtime_contract.py:162-177` exige
  `onnx` et `onnxruntime` même en mode `validation`.
- S7 — notebook : `SOURCE_BUNDLE_SHA256` calculé sur l'arbre copié, donc
  inconnaissable a priori ; `run_cli` avec `capture_output=True` perd la
  stderr des échecs.
- S8 — double sélection sur la même validation (checkpoint puis seuil), IC
  bootstrap sur 9 grappes, aucune métrique train pour la baseline
  (sur-apprentissage ExtraTrees non mesurable).
- S9 — environnements fragmentés : Python 3.13.5 pour les rapports baseline
  et BBBC019, 3.12.14 pour le CNN, smoke lancé depuis
  `data/cache/microsam-env` ; `uv.lock` ne couvre ni le CNN ni µSAM.

### Faible

Trois implémentations divergentes des métriques binaires
(`split_ooc.py`, `train_ooc_baseline.py`, `ooc_cnn/metrics.py`) ;
`benchmark.py:170-171` note 0 une image sans vérité ni prédiction ; masques
`reannotation` BBBC019 inutilisés pour estimer un plafond inter-annotateur ;
archive OoC vérifiée par md5 seul ; `final-eval` re-hache 7 Go inutilement ;
`training/train.py` est un stub mort ; `export.py` accepte un rapport `smoke`.

## Constats produit (backend)

### Élevé

| # | Constat | Preuve | Recommandation |
|---|---|---|---|
| B1 | **TIFF 16 bits rendu blanc** : `convert("L")` écrête au lieu de remettre à l'échelle. Reproduit : même contenu, 0 objet et deux avertissements faux en `I;16`, 1 objet en 8 bits. Les jeux actuels sont en 8 bits, donc les benchmarks restent valides, mais la promesse « import TIFF de microscopie » ne l'est pas. | `pipeline.py:106-107`, `benchmark.py:287-288` | normaliser selon le dtype (`img_as_float`) avant Otsu et pour l'overlay ; test dédié |
| B2 | **Bombe de décompression** : `DecompressionBombError` non interceptée → 500, fichier orphelin compté, puis expérience bloquée en `analyzing` ; un PNG uniforme 10 000² (97 Ko) est accepté et décode 100 Mpx (≈ 50 o/pixel mesurés, ≈ 5 Go). | `experiments.py:50`, `:92`, `:133-144`, `pipeline.py:108` | `MAX_IMAGE_PIXELS` projet, contrôle des dimensions à l'upload, `except Exception` avec passage en `failed` |

### Moyen

- B3 — statut `analyzing` persistant sur toute exception non `ValueError`,
  y compris après redémarrage (aucune réconciliation).
- B4 — nom de fichier > 255 octets → 500 (`unlink` relève `OSError`).
- B5 — limite 25 Mo appliquée après réception complète ; port 8000 publié sur
  l'hôte, contournant nginx ; aucun quota.
- B6 — analyse synchrone ≈ 0,66 s/Mpx : un lot de 20 images 16 Mpx dépasse le
  `proxy_read_timeout` de 120 s ; relances concurrentes non idempotentes.
- B7 — polarité choisie par a priori de couverture 18 % : sur une monocouche
  confluente, les « objets » sont les interstices.
- B8 — `mean_object_area` moyennée avec des zéros pour les images vides ;
  `mean_equivalent_diameter` jamais agrégé.
- B9 — `cp .env.example .env` fixe `ORGANCHIP_DATA_DIR=/data` et casse le
  mode local (`OSError` à l'import) ; `ORGANCHIP_MAX_UPLOAD_MB` non transmis
  par compose.
- B10 — « vérification de contenu » réelle pour PNG seulement (`verify()`
  est un no-op JPEG/TIFF) ; un JPEG tronqué est accepté puis échoue à
  l'analyse.

### Faible

Connexions SQLite jamais fermées ; `PRAGMA foreign_keys` inactif ; anciens
résultats servis après un upload rejeté ; JSON persisté sans migration ;
`GET /artifacts` crée un dossier par effet de bord et force `attachment` ;
Docker en root, `pip install .` sans `uv.lock` (l'image livrée n'est pas la
résolution testée), pas de build d'image en CI, périmètre ruff CI sans
`backend/scripts` ; `resource` importé (Unix seulement) ; identifiants de
moteur du registre (`micro-sam-pretrained`) et du benchmark
(`micro-sam-vit-b-lm-apg`) déconnectés ; validateur de registre re-exécuté à
chaque appel et sur-testé par monkeypatch.

Tests manquants : `GET /results` (200/404), persistance des résultats après
redémarrage, échec d'analyse → `failed`, JPEG/TIFF/16 bits, limite de taille,
CLI `inference.py`, concurrence.

frontend ; `App.tsx` monolithique (567 lignes) ; focus clavier invisible sur
